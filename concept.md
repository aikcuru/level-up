# Level Up — концепция проекта

## 1. Название проекта

**Level Up** — геймифицированный планировщик для ученицы 11 класса.

## 2. Краткое описание

Level Up — одностраничное веб-приложение для планирования школьных заданий, подготовки к ЕГЭ, олимпиад, поступления и личных дел.

Пользователь создаёт задачи, указывает направление, предмет, срок выполнения и сложность. За выполнение задачи начисляются очки опыта — XP. Накопление XP повышает уровень пользователя и визуально показывает общий прогресс.

Приложение должно помочь хранить разные виды задач в одном месте, видеть ближайшие дедлайны и не терять информацию о том, сколько раз срок выполнения задачи переносился.

Проект создаётся как учебная первая версия — MVP. Он должен быть достаточно простым для реализации на HTML, CSS и JavaScript, но при этом полезным для реального пользователя.

## 3. Целевая аудитория

Основной пользователь приложения — ученица 11 класса, которая одновременно:

- выполняет школьные задания;
- готовится к ЕГЭ;
- участвует в олимпиадах;
- готовится к поступлению;
- планирует личные дела.

В первой версии приложение рассчитано на одного пользователя.

## 4. Проблема пользователя

В 11 классе одновременно появляется большое количество задач с разными сроками и приоритетами.

Задачи могут относиться к разным направлениям:

- текущая школьная учёба;
- подготовка к обязательным экзаменам;
- подготовка к дополнительным экзаменам;
- олимпиады;
- выбор университета и поступление;
- личные дела.

При использовании обычного списка задач сложно быстро понять:

- к какому направлению относится задача;
- с каким предметом она связана;
- сколько времени осталось до дедлайна;
- какие задачи уже просрочены;
- какие задачи переносились;
- сколько раз изменялся срок;
- какие задачи уже выполнены;
- как продвигается общий прогресс.

Level Up должен объединить эти данные в одном понятном интерфейсе.

## 5. Цель проекта

Создать удобный и визуально приятный планировщик, который помогает:

- собирать задачи разных типов в одном месте;
- контролировать сроки;
- видеть просроченные задачи;
- отслеживать переносы дедлайнов;
- отмечать выполненные дела;
- получать понятную визуальную обратную связь;
- поддерживать интерес к регулярному выполнению задач с помощью XP и уровней.

Приложение не должно выглядеть как корпоративная система управления проектами.

## 6. Формат приложения

Первая версия Level Up будет одностраничным веб-приложением.

Приложение должно корректно отображаться:

- на компьютере;
- на планшете;
- на телефоне.

Интерфейс должен быть адаптивным: блоки, кнопки, формы и карточки задач должны подстраиваться под ширину экрана.

## 7. Направления задач

Каждая задача должна относиться к одному из следующих направлений:

1. Школа.
2. ЕГЭ.
3. Олимпиады.
4. Поступление.
5. Личные дела.

Направление выбирается при создании или редактировании задачи.

## 8. Учебные предметы

По умолчанию в приложении должны быть доступны:

- русский язык;
- математика.

Дополнительные экзаменационные предметы пока не определены, поэтому пользователь должен иметь возможность самостоятельно добавлять новые предметы.

Примеры дополнительных предметов:

- обществознание;
- английский язык;
- информатика;
- физика;
- история;
- литература.

Для задач из направления «Личные дела» выбор учебного предмета не является обязательным.

Добавленные пользователем предметы должны сохраняться после перезагрузки страницы.

## 9. Основные возможности первой версии

Пользователь должен иметь возможность:

- создать новую задачу;
- указать название задачи;
- выбрать направление;
- выбрать учебный предмет;
- добавить новый предмет;
- установить дедлайн;
- выбрать сложность задачи;
- увидеть количество XP за выполнение;
- редактировать активную задачу;
- переносить дедлайн;
- видеть количество переносов дедлайна;
- отметить задачу выполненной;
- удалить задачу;
- просматривать активные задачи;
- просматривать выполненные задачи;
- фильтровать задачи;
- видеть срок выполнения;
- видеть, сколько времени осталось до дедлайна;
- видеть просроченные задачи;
- получать XP за выполненные задачи;
- повышать уровень;
- сохранять задачи и прогресс после перезагрузки страницы.

## 10. Создание задачи

Для создания задачи пользователь заполняет форму.

Форма должна содержать следующие поля:

- название задачи;
- направление;
- предмет;
- сложность;
- дедлайн.

Обязательные поля:

- название;
- направление;
- сложность;
- дедлайн.

Для учебных направлений предмет должен быть обязательным.

Для направления «Личные дела» задача может быть создана без предмета.

Перед сохранением приложение должно проверить обязательные поля.

Если обязательное поле не заполнено, задача не создаётся, а пользователь видит понятное сообщение об ошибке.

После успешного сохранения новая задача появляется в списке активных задач.

## 11. Сложность задачи и XP

В первой версии используется три уровня сложности:

- простая задача — 5 XP;
- средняя задача — 20 XP;
- сложная задача — 50 XP.

Количество XP определяется выбранной сложностью.

Пользователь не вводит XP вручную.

После выполнения задачи XP начисляются только один раз.

Повторное нажатие на выполненную задачу не должно повторно начислять XP.

## 12. Выполнение задачи

У каждой активной задачи должна быть кнопка или элемент управления «Выполнено».

После выполнения задачи:

- её статус меняется на выполненный;
- она перемещается в список выполненных задач;
- пользователю начисляется XP;
- обновляется шкала прогресса;
- при необходимости повышается уровень.

После завершения задачи её основные параметры фиксируются.

В первой версии выполненную задачу нельзя редактировать способом, который изменит уже начисленное количество XP.

## 13. Редактирование задачи

У каждой активной задачи должна быть кнопка «Редактировать».

При редактировании пользователь может изменить:

- название;
- направление;
- предмет;
- сложность;
- дедлайн.

Изменения применяются только после нажатия кнопки «Сохранить».

До сохранения пользователь должен иметь возможность отменить редактирование без изменения задачи.

Редактирование названия, направления, предмета или сложности не должно увеличивать счётчик переносов дедлайна.

## 14. Перенос дедлайна

При создании задачи приложение сохраняет первоначальный дедлайн.

Если при редактировании пользователь устанавливает дату позже текущего дедлайна, это считается переносом.

В этом случае:

- новый дедлайн сохраняется;
- счётчик переносов увеличивается на единицу;
- первоначальный дедлайн не изменяется.

Если пользователь переносит дедлайн несколько раз, приложение показывает общее количество переносов.

Если пользователь изменяет дедлайн на более раннюю дату, счётчик переносов не увеличивается.

Если пользователь несколько раз меняет дату в форме редактирования, но сохраняет изменения только один раз, это считается одним переносом.

Изменение других полей задачи не считается переносом.

## 15. Отображение количества переносов

Количество переносов должно отображаться в карточке задачи.

Правила отображения:

- если дедлайн ни разу не переносился, информация о переносах может не показываться;
- после одного переноса отображается текст: «Дедлайн перенесён: 1 раз»;
- после нескольких переносов отображается фактическое количество переносов.

Примеры:

- «Дедлайн перенесён: 1 раз»;
- «Дедлайн перенесён: 2 раза»;
- «Дедлайн перенесён: 5 раз».

Счётчик переносов должен сохраняться после перезагрузки страницы.

## 16. Отображение дедлайна

В карточке задачи должны отображаться:

- текущая дата дедлайна;
- количество оставшихся дней;
- статус срока;
- количество переносов, если они были.

Возможные состояния:

- дедлайн ещё не наступил;
- дедлайн сегодня;
- задача просрочена;
- задача выполнена.

Просроченные задачи должны визуально отличаться от остальных.

Например, можно использовать:

- рамку;
- значок;
- подпись «Просрочено»;
- отдельный акцентный оттенок.

Цвет не должен быть единственным способом передачи статуса. Дополнительно должен использоваться текст или значок.

## 17. Фильтрация задач

Пользователь должен иметь возможность отфильтровать задачи:

- по статусу;
- по направлению.

Фильтр по статусу:

- все;
- активные;
- выполненные;
- просроченные.

Фильтр по направлению:

- все направления;
- школа;
- ЕГЭ;
- олимпиады;
- поступление;
- личные дела.

В первой версии поиск по тексту и сложная сортировка не являются обязательными.

## 18. Удаление задачи

У каждой задачи должна быть кнопка «Удалить».

Перед удалением приложение должно запросить подтверждение, чтобы задача не была удалена случайно.

После подтверждения задача удаляется из списка и из локального хранилища.

Удаление выполненной задачи не должно изменять уже начисленный общий XP.

## 19. Профиль пользователя

На главном экране должен отображаться профиль пользователя.

Профиль содержит:

- имя или никнейм;
- текущий уровень;
- текущее количество XP;
- количество XP до следующего уровня;
- шкалу прогресса.

В первой версии имя или никнейм может задаваться пользователем и сохраняться в браузере.

Аватар, магазин предметов и сложная система персонажей в первую версию не входят.

## 20. Система уровней

Для повышения уровня требуется набрать 100 XP.

Пример:

- уровень 1: от 0 до 99 XP;
- уровень 2: от 100 до 199 XP;
- уровень 3: от 200 до 299 XP.

После достижения очередных 100 XP уровень увеличивается.

Шкала прогресса показывает XP внутри текущего уровня.

Например, если пользователь набрал 135 XP:

- текущий уровень — 2;
- прогресс внутри уровня — 35 из 100 XP.

## 21. Основные блоки интерфейса

Страница должна содержать следующие блоки:

1. Шапка приложения.
2. Профиль пользователя.
3. Шкала XP и уровень.
4. Форма создания задачи.
5. Управление дополнительными предметами.
6. Фильтры.
7. Список активных задач.
8. Список выполненных задач.

На телефоне блоки должны располагаться вертикально.

На компьютере часть блоков может располагаться в несколько колонок, если это не ухудшает читаемость.

## 22. Карточка задачи

Карточка задачи должна содержать:

- название;
- направление;
- предмет, если он указан;
- сложность;
- количество XP;
- текущий дедлайн;
- оставшееся время;
- статус;
- количество переносов дедлайна;
- кнопку выполнения;
- кнопку редактирования;
- кнопку удаления.

Карточка не должна быть перегружена декоративными элементами.

Главная информация должна быть заметна без открытия дополнительных окон.

## 23. Визуальный стиль

Выбранный стиль — уютный пастельный интерфейс в коричневых оттенках.

Основные визуальные характеристики:

- светлый кремовый фон;
- бежевые карточки;
- светло-коричневые элементы;
- тёмно-коричневый текст;
- мягкие границы;
- скруглённые углы;
- спокойные акцентные оттенки;
- достаточный контраст текста и фона.

Возможные оттенки:

- кремовый;
- молочный;
- песочный;
- карамельный;
- кофейный;
- приглушённый терракотовый.

Интерфейс должен быть современным, спокойным и дружелюбным.

Дизайн не должен выглядеть слишком детским или слишком официальным.

## 24. Анимации

Допускаются лёгкие анимации:

- плавное заполнение шкалы XP;
- появление новой карточки;
- визуальная реакция на выполнение задачи;
- плавное открытие формы редактирования.

Анимации не должны:

- замедлять работу;
- мешать чтению;
- использоваться слишком часто;
- быть обязательными для понимания интерфейса.

## 25. Адаптивность

Приложение должно быть удобно использовать на экранах разной ширины.

На телефоне:

- форма должна помещаться по ширине экрана;
- текст не должен выходить за границы;
- кнопки должны быть достаточно крупными для нажатия;
- карточки должны располагаться в одну колонку;
- горизонтальная прокрутка страницы не должна появляться.

На компьютере:

- контент не должен растягиваться на всю ширину большого экрана;
- блоки должны оставаться читаемыми;
- основные действия должны быть видны без лишних переходов.

## 26. Хранение данных

В первой версии данные хранятся в `localStorage` браузера.

Должны сохраняться:

- имя или никнейм;
- текущий XP;
- текущий уровень;
- список задач;
- статусы задач;
- первоначальные дедлайны;
- текущие дедлайны;
- количество переносов каждой задачи;
- список дополнительных предметов.

После перезагрузки страницы данные не должны исчезать.

## 27. Ограничение хранения данных

`localStorage` хранит данные только в браузере конкретного устройства.

Это означает:

- задачи, добавленные на компьютере, не появятся автоматически на телефоне;
- задачи, добавленные на телефоне, не появятся автоматически на компьютере;
- очистка данных браузера может удалить сохранённые задачи;
- приложение не предоставляет резервное копирование данных.

Сайт будет доступен и на компьютере, и на телефоне, но синхронизация между устройствами в первую версию не входит.

Для синхронизации потребовались бы:

- база данных;
- серверная часть или облачный сервис;
- регистрация и авторизация пользователя.

Это может быть добавлено в будущей версии.

## 28. Технологии

Для разработки первой версии используются:

- HTML5;
- CSS3;
- JavaScript;
- localStorage;
- Git;
- GitHub;
- GitHub Pages.

Проект создаётся без React и без других JavaScript-фреймворков.

В первой версии также не используются:

- сервер;
- база данных;
- система авторизации;
- платные API;
- внешняя система управления состоянием.

## 30. Что входит в MVP

В обязательную первую версию входят:

- профиль пользователя;
- XP и уровни;
- создание задачи;
- редактирование активной задачи;
- удаление задачи;
- выполнение задачи;
- выбор направления;
- выбор предмета;
- добавление дополнительных предметов;
- три уровня сложности;
- автоматическое определение XP;
- дедлайны;
- отображение просроченных задач;
- перенос дедлайна;
- счётчик переносов;
- фильтрация;
- адаптивный интерфейс;
- сохранение данных в localStorage;
- публикация на GitHub Pages.

## 31. Что не входит в MVP

В первую версию не входят:

- регистрация;
- авторизация;
- синхронизация между устройствами;
- серверная база данных;
- совместная работа нескольких пользователей;
- уведомления операционной системы;
- отправка уведомлений на электронную почту;
- интеграция со школьным электронным дневником;
- импорт школьного расписания;
- импорт дат ЕГЭ;
- автоматический импорт олимпиад;
- полноценный календарь;
- интерактивная временная шкала;
- магазин наград;
- виртуальная валюта;
- аватары;
- сложная система достижений;
- звуковые эффекты;
- искусственный интеллект внутри приложения;
- мобильное приложение для App Store или Google Play.

Эти функции можно рассматривать только после завершения и проверки первой версии.

## 32. Критерии готовности

Проект считается готовым, если выполнены все условия:

- Пользователь может открыть приложение в браузере.
- Интерфейс корректно отображается на компьютере.
- Интерфейс корректно отображается на телефоне.
- Пользователь может указать имя или никнейм.
- Пользователь может создать новую задачу.
- Обязательные поля проверяются перед сохранением.
- Новая задача появляется в списке.

## 34. Итоговая формулировка проекта

Level Up — адаптивный геймифицированный планировщик для ученицы 11 класса.

Приложение объединяет школьные задания, подготовку к ЕГЭ, олимпиады, поступление и личные дела. Пользователь может создавать и редактировать задачи, добавлять учебные предметы, переносить дедлайны, видеть количество переносов, отмечать задачи выполненными и получать XP.

Первая версия работает без сервера и сохраняет данные в браузере с помощью localStorage. Интерфейс выполнен в уютном пастельном стиле с коричневыми оттенками и адаптирован для компьютера и телефона.
