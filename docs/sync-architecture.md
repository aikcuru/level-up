# Архитектура синхронизации Level Up

## 1. Цель этапа

Цель этапа — обеспечить синхронизацию профиля, учебных предметов и задач Level Up между компьютером и телефоном через сервер.

Сервер становится источником истины для пользовательских данных. Клиентское приложение продолжает предоставлять существующие функции планировщика, но подтверждает сохранение изменений только после успешного ответа сервера.

## 2. Границы первой версии

- используется один закрытый личный аккаунт;
- публичная регистрация отсутствует;
- архитектура и все пользовательские записи изначально разделяются по `userId`, чтобы позднее можно было добавить других пользователей;
- основное приложение работает через `https://levelup.aikcu.ru`;
- GitHub Pages остаётся резервной статической публикацией;
- серверная синхронизация на резервной публикации GitHub Pages работать не обязана;
- офлайн-очередь, автоматическое объединение конфликтующих изменений и публичное управление аккаунтами в первую версию не входят.

## 3. Согласованный способ входа

### Логин

- Для входа используются логин и пароль.
- Длина логина составляет от 3 до 32 символов.
- Разрешены латинские буквы, цифры, точка, дефис и подчёркивание.
- Пробелы и кириллица не разрешены.
- Регистр не учитывается: перед сравнением и хранением логин нормализуется в нижний регистр.
- Логин не должен содержать личные данные.
- Логин не используется как отображаемое имя; эти значения не обязаны совпадать.

### Пароль

- Минимальная длина пароля — 6 символов.
- Разрешены буквы, цифры, пробелы и специальные символы.
- Обязательное наличие заглавной буквы, цифры или специального символа не требуется.
- Очевидные слабые пароли, включая `123456` и `qwerty`, запрещены.
- Пароль не должен совпадать с нормализованным логином.
- Интерфейс может рекомендовать 8 символов и больше, но не требовать этого.
- Пароль хранится только как защищённый медленный хеш; предпочтительный алгоритм — Argon2id.
- Исходный пароль, временный пароль и хеш не должны попадать в Git, журналы или историю команд.

### Создание аккаунта и первоначальная настройка

- Аккаунт создаётся интерактивной административной командой на сервере; публичной регистрации нет.
- Логин и временный пароль не передаются аргументами командной строки.
- Временный пароль вводится скрыто.
- Повторное создание того же нормализованного логина запрещено.
- Профиль создаётся без отображаемого имени.
- Аккаунт получает признак обязательной первоначальной настройки.
- При первом входе пользователь обязан установить новый постоянный пароль, повторить его и ввести отображаемое имя.
- Основной интерфейс открывается только после успешной первоначальной настройки.
- Позднее отображаемое имя можно изменить в настройках.
- Восстановление пароля в первой версии выполняется администратором.

### Срок и проверка сессии

- Сессия действует ровно 30 дней с момента входа.
- Фоновая активность и проверка `syncVersion` не продлевают срок сессии.
- Закрытие браузера не завершает сессию.
- При запуске приложение сначала проверяет сессию и до завершения проверки не показывает основной интерфейс.
- Если сессия отсутствует или истекла, сразу показывается форма входа.
- Если сессия истекла в уже открытом приложении, изменяющие действия блокируются и показывается экран повторного входа.
- Введённые, но ещё не сохранённые значения формы не очищаются при повторном входе.
- После повторного входа восстанавливаются сохранённые серверные данные.
- Обычный выход завершает текущую сессию.
- Смена или административный сброс пароля завершает все сессии и требует нового входа.

### Несколько устройств

- Телефон и компьютер используют отдельные серверные сессии.
- Одновременная работа нескольких устройств разрешена.
- Каждая сессия имеет собственный срок 30 дней.
- В базе хранится только защищённое представление идентификатора сессии.
- Обычный выход завершает только текущую сессию.
- Действие «Выйти на всех устройствах» завершает все сессии.
- На аккаунт разрешено не более 10 активных сессий.
- При создании одиннадцатой сессии сервер завершает самую старую активную сессию.

### Маршруты авторизации

- `POST /api/v1/auth/login`;
- `GET /api/v1/auth/session`;
- `POST /api/v1/auth/complete-setup`;
- `POST /api/v1/auth/change-password`;
- `POST /api/v1/auth/logout`;
- `POST /api/v1/auth/logout-all`.

При обычной смене пароля пользователь вводит текущий пароль, новый пароль и повтор нового пароля. После успешной смены все активные сессии завершаются.

### Защита от перебора пароля

- После 5 неудачных попыток входа за 15 минут новые попытки блокируются на 15 минут.
- Счётчик учитывает сочетание нормализованного логина и IP-адреса.
- Успешный вход сбрасывает соответствующий счётчик.
- Постоянная блокировка аккаунта не применяется.
- Ответ об ошибке не раскрывает, существует ли введённый логин.
- Журналы не содержат пароль, cookie, session token или CSRF token.

## 4. Согласованный серверный стек

- Python 3.12;
- FastAPI;
- Uvicorn;
- SQLite;
- systemd;
- Nginx.

API слушает только `127.0.0.1`. Внешние запросы к API принимает Nginx по существующему HTTPS-соединению и передаёт их внутреннему процессу приложения. Новые внешние порты не открываются.

В первой версии не используются:

- MySQL;
- PostgreSQL;
- Node.js;
- Docker.

| Компонент | Расположение |

| Код API | `/opt/levelup-api` |

| Секреты и параметры окружения | `/etc/levelup-api/levelup-api.env` |

Код API рекомендуется хранить в отдельном репозитории, а не в публичном каталоге статического сайта. Репозиторий API на этом этапе не создаётся.

API имеет версию `v1`. Версия API не связана с `version` отдельных записей или общей `syncVersion` аккаунта.

## 6. Модель данных

Ниже описаны минимальные логические сущности без привязки к SQL-синтаксису. Все пользовательские записи должны быть связаны с `userId`. Для изменяемых записей предусматриваются `id`, `version`, `createdAt`, `updatedAt` и, при мягком удалении, `deletedAt`.

### `users`

Хранит закрытые учётные записи:

- `id`, используемый как `userId` для связанных данных;
- логин и его нормализованное представление;
- защищённый хеш пароля;
- состояние учётной записи;
- признак обязательной первоначальной настройки;
- `version`, `createdAt`, `updatedAt`, при необходимости `deletedAt`.

Логин должен быть уникальным. Пароль и данные действующих сессий не возвращаются клиентскому приложению.

### `profiles`

Хранит пользовательский профиль:

- `id`;
- `userId`;
- отображаемое имя;
- признак завершения первоначальной настройки имени;
- `version`, `createdAt`, `updatedAt`, при необходимости `deletedAt`.

`totalXp` и `level` не являются самостоятельным источником истины: сервер вычисляет их по задачам.

### `subjects`

Хранит доступные пользователю предметы:

- `id`;
- `userId`;
- название;
- нормализованное название для запрета дубликатов без учёта регистра;
- признак системного или пользовательского предмета, если он потребуется контракту;
- `version`, `createdAt`, `updatedAt`, `deletedAt`.

### `tasks`

Хранит задачи пользователя:

- `id`;
- `userId`;
- `title`;
- `direction`;
- связь с предметом или отсутствие предмета;
- `difficulty`;
- `xpReward`;
- `status`;
- `originalDeadline`;
- `currentDeadline`;
- `postponementCount`;
- `xpAwarded`;
- `version`, `createdAt`, `updatedAt`, `deletedAt`.

Сервер проверяет допустимые направления, обязательность предмета, даты, сложность, награду и согласованность `status` с `xpAwarded`.

### `sessions`

Хранит серверные сессии:

- `id`;
- `userId`;
- безопасное представление идентификатора сессии;
- время создания;
- фиксированное время истечения через 30 дней после входа;
- время отзыва или завершения;
- необходимые служебные признаки безопасности.

Срок не продлевается фоновой активностью. Для одного аккаунта одновременно действует не более 10 сессий; при создании одиннадцатой отзывается самая старая активная сессия. Исходный session token не должен попадать в журналы или возвращаться через API, кроме защищённой cookie установленного формата.

### Версия состояния аккаунта

Для каждого пользователя хранится монотонно увеличивающаяся `syncVersion`. Она изменяется после подтверждённого изменения профиля, предмета, задачи или удаления записи.

Клиент использует `syncVersion`, чтобы определить, появились ли изменения на другом устройстве. `syncVersion` не заменяет версии отдельных записей и не используется для разрешения конфликтов между разными задачами.

### Идемпотентные операции

Для изменяющих запросов хранится информация об уже обработанных операциях:

- `id`;
- `userId`;
- уникальный случайный UUID клиентской операции из заголовка `Idempotency-Key`;
- тип операции;
- отпечаток запроса;
- состояние обработки;
- ссылка на затронутую запись или безопасно сохранённый результат;
- `createdAt` и срок хранения 24 часа.

Новое пользовательское действие получает новый ключ, а повтор того же сетевого запроса использует прежний. Повтор запроса с тем же ключом и содержимым возвращает прежний результат без повторного эффекта. Тот же ключ с другим содержимым отклоняется с кодом `409`, отсутствие обязательного ключа — с кодом `400`. Запись идемпотентной операции и изменение пользовательских данных выполняются в одной транзакции SQLite. Ключ не содержит личные данные.

Задачи и пользовательские предметы получают UUID на клиенте. База запрещает повторение их ID в пределах одного пользователя.

### Версии записей

Профиль, предмет и задача имеют независимое целочисленное поле `version`:

- начальное значение — `1`;
- после каждого успешного изменения значение увеличивается на `1`;
- `version` является счётчиком и не требует хранения полного архива копий;
- отдельные задачи имеют независимые версии;
- сервер возвращает версию записи через `ETag`;
- изменение и удаление требуют заголовок `If-Match`;
- отсутствующий `If-Match` возвращает `428`;
- несовпадение версии возвращает `412`;
- мягко удалённая задача возвращает `410`;
- запись другого пользователя не раскрывается и возвращает `404`;
- ответ о конфликте содержит актуальные `version`, `syncVersion` и актуальную запись, если она не удалена.

Общая `syncVersion` аккаунта увеличивается после каждого подтверждённого изменения и служит только для обнаружения новых данных.

### Время и часовой пояс

- Часовой пояс аккаунта — `Asia/Irkutsk`.
- Пользовательские дедлайны остаются календарными датами без времени.
- Состояния «Сегодня» и «Просрочено» рассчитываются по календарной дате `Asia/Irkutsk`.
- Настройки часового пояса устройства не должны менять статус дедлайна.
- Технические метки `createdAt`, `updatedAt`, `deletedAt` и время истечения сессии хранятся в UTC.
- Расписание резервного копирования использует отдельный часовой пояс `Europe/Moscow`.

### Мягко удалённые записи

Удалённая запись сохраняется с заполненным `deletedAt` и остаётся доступной серверной логике контроля версий в течение 30 дней. Она не возвращается в обычных пользовательских списках и не может быть восстановлена устаревшим обновлением с другого устройства.

## 7. XP и уровни

- Задачи являются источником истины для XP.
- `totalXp` вычисляется как сумма `xpReward` всех неудалённых выполненных задач.
- `level` вычисляется по действующей формуле из `totalXp`.
- `totalXp` не может быть отрицательным.
- `xpReward` обязан соответствовать `difficulty`: `easy` — 5 XP, `medium` — 20 XP, `hard` — 50 XP.
- Выполнение разрешено только для активной задачи, за которую XP ещё не начислен.
- Выполнение задачи является идемпотентной операцией.
- Повторный запрос не должен начислять XP второй раз.
- Удаление выполненной задачи исключает её награду из пересчитанного `totalXp` и может уменьшить уровень.
- Клиентские значения `totalXp`, `level` и `xpReward` не принимаются сервером без проверки и пересчёта.

## 8. Правила синхронизации

### Формат API

- Используется REST API с JSON.
- Базовый адрес — `https://levelup.aikcu.ru/api/v1/`.
- Группы маршрутов: `/api/v1/auth/`, `/api/v1/profile/`, `/api/v1/subjects/`, `/api/v1/tasks/` и `/api/v1/sync/`.
- Клиент не отправляет `userId`; сервер определяет пользователя по действующей сессии.
- GraphQL и WebSocket в первой версии не используются.

Базовые коды ответа:

| Код | Значение |
|---|---|
| `400` | Неверный запрос или отсутствующий обязательный `Idempotency-Key`. |
| `401` | Сессия отсутствует или истекла. |
| `403` | Действие запрещено или не пройдена CSRF-проверка. |
| `404` | Запись отсутствует либо недоступна текущему пользователю. |
| `409` | Бизнес-конфликт, например повтор предмета или повтор ключа с другим содержимым. |
| `410` | Запись была удалена. |
| `412` | Версия записи устарела. |
| `422` | Ошибка проверки данных. |
| `428` | Отсутствует обязательное условие `If-Match`. |
| `500` | Внутренняя ошибка без раскрытия путей, стека и секретов. |

### Загрузка данных

- `GET /api/v1/state` возвращает полный снимок при запуске и ручном обновлении.
- Снимок содержит профиль, предметы, неудалённые задачи, `totalXp`, `level`, `syncVersion` и серверное время.
- `GET /api/v1/sync/version` выполняет лёгкую фоновую проверку общей версии аккаунта.
- Весь объект `levelUpState` целиком серверу не отправляется.
- Создание, изменение, выполнение и удаление выполняются отдельными запросами.
- После изменения сервер возвращает обновлённую запись, её `version`, новую `syncVersion`, а при необходимости — пересчитанные XP и уровень.

Маршруты задач:

- `POST /api/v1/tasks`;
- `PATCH /api/v1/tasks/{taskId}`;
- `POST /api/v1/tasks/{taskId}/complete`;
- `DELETE /api/v1/tasks/{taskId}`.

### Обновление между устройствами

- Изменения профиля, предметов и задач отправляются на сервер сразу после пользовательского действия.
- Интерфейс считает изменение сохранённым только после успешного ответа сервера.
- На время изменяющего запроса соответствующие кнопки блокируются.
- Данные другого устройства полностью загружаются при запуске приложения или после ручного обновления.
- Открытая страница проверяет `syncVersion` примерно раз в 30 секунд, при возвращении пользователя на вкладку и после восстановления окна.
- Если серверная `syncVersion` изменилась, приложение показывает постоянное уведомление о новых данных.
- Автоматическая перезагрузка страницы или автоматическая замена открытых данных не выполняется.
- В уведомлении или связанном интерфейсе доступна кнопка «Обновить».
- Если пользователь начал ввод или редактирование и ещё не отправил данные, перед обновлением показывается предупреждение о потере незавершённого ввода.
- Обновление данных не должно выполняться скрыто, если оно способно заменить введённые, но не сохранённые значения.
- Проверка `syncVersion` не продлевает срок сессии.

### Идемпотентность запросов

- Для всех изменяющих операций обязателен заголовок `Idempotency-Key` со случайным UUID.
- Новое пользовательское действие получает новый ключ; повтор сетевого запроса использует прежний ключ.
- Сервер хранит ключ, отпечаток запроса и результат 24 часа.
- Повтор того же запроса возвращает прежний результат без повторного эффекта.
- Тот же ключ с другим содержимым возвращает `409`, отсутствие обязательного ключа — `400`.
- Запись операции и изменение данных выполняются в одной транзакции SQLite.

## 9. Конфликты

- Каждая изменяемая запись имеет собственное поле `version`.
- Сервер возвращает `ETag`, а клиент отправляет базовую версию через `If-Match`.
- Сервер принимает обновление только при совпадении базовой и актуальной версии.
- Отсутствующий `If-Match` возвращает `428`.
- Устаревшее изменение возвращает `412` и не затирает новые данные.
- После конфликта пользователь загружает актуальную версию и при необходимости повторяет действие.
- Изменения разных задач не должны конфликтовать друг с другом только потому, что изменилось общее состояние аккаунта.
- `syncVersion` сообщает о наличии изменений, а версия конкретной записи защищает её от перезаписи.
- Мягко удалённая задача возвращает `410`, сохраняет информацию о версии и не восстанавливается запросом, основанным на старой версии.
- Запись другого пользователя не раскрывается и возвращает `404`.
- Ответ о конфликте содержит актуальные `version`, `syncVersion` и актуальную запись, если она не удалена.
- Сервер является окончательным арбитром версии записи и допустимости перехода состояния.

## 10. Работа без интернета

- Просмотр последнего подтверждённого сервером снимка из локального кэша допустим.
- Создание, редактирование, выполнение и удаление требуют доступного соединения с сервером.
- Офлайн-очередь в первой версии отсутствует.
- При отсутствии сети и доступном кэше показывается сообщение: «Нет соединения. Показаны данные, загруженные ранее».
- Если кэша нет, без интернета показывается ошибка подключения.
- При отсутствии сети или ошибке сервера интерфейс не сообщает об успешном сохранении.
- Локальное представление не должно окончательно расходиться с подтверждённым серверным состоянием.
- Повторное нажатие или повтор запроса не должны создавать дубликаты благодаря идентификатору операции.
- Кнопки изменяющего действия блокируются до получения ответа или завершения запроса ошибкой.
- После восстановления соединения пользователь повторяет действие вручную либо обновляет данные с сервера.

## 11. Удаление

- В первой версии мягкое удаление применяется только к задачам.
- Профиль и предметы не получают пользовательских операций удаления в первой версии.
- Наличие поля `deletedAt` в общей концептуальной модели не означает появления такой функции в интерфейсе или API.
- Удаление других сущностей потребует отдельного решения и обновления `concept.md` и `tz.md`.
- После успешного ответа сервера удалённая задача сразу скрывается из интерфейса.
- Время удаления записывается в `deletedAt`.
- Мягко удалённая задача хранится 30 дней.
- Пользовательской кнопки восстановления в первой версии нет.
- Устаревшие изменения не могут снять `deletedAt` или создать удалённую задачу заново с тем же ID.
- Окончательное удаление выполняется отдельным обслуживанием базы после истечения срока хранения.

## 12. Переход с `localStorage`

- Реальных пользовательских задач в текущем `localStorage` нет.
- Тестовые задачи, предметы, XP и профиль не импортируются на сервер.
- Серверный аккаунт начинает работу с пустым состоянием.
- Текущий `levelUpState` не удаляется автоматически до завершения проверки серверной версии.
- После успешной проверки потребуется отдельное безопасное действие для очистки тестовых данных.
- До такого действия должна сохраняться возможность сравнить серверную версию с прежним локальным приложением.
- `localStorage` используется только как кэш последнего подтверждённого сервером снимка.
- Сервер всегда остаётся источником истины.
- Пароли, session token, cookie и CSRF token в `localStorage` не хранятся.
- Без интернета кэш доступен только для просмотра, а изменяющие действия блокируются.
- После восстановления связи клиент загружает серверное состояние и заменяет им кэш.
- Повреждённый или устаревший локальный кэш не должен удалять или изменять серверные данные.
- Если кэша нет, без интернета приложение показывает ошибку подключения.

## 13. Безопасность

- Пароли, хеши паролей, session token, ключи, секреты и содержимое секретных конфигураций не хранятся в Git.
- API и база располагаются вне `/var/www`.
- Файл SQLite недоступен через Nginx и публичные URL.
- API запускается от отдельного системного пользователя без SSH-входа.
- Каталоги, база, резервные копии, конфигурация окружения и systemd unit получают минимально необходимые права.
- Сервер повторно проверяет все входные данные независимо от клиентской валидации.
- Любой запрос к профилю, предметам и задачам ограничивается авторизованным `userId` текущей сессии.
- Клиент не может выбрать произвольный `userId` и получить чужие данные.
- API работает в рамках того же origin `https://levelup.aikcu.ru`; публичный CORS не включается.
- Сессионная cookie имеет атрибуты `Secure`, `HttpOnly` и `SameSite=Lax`.
- После входа сервер выдаёт отдельный CSRF-токен.
- JavaScript хранит CSRF-токен только в памяти страницы; в `localStorage` он не записывается.
- Изменяющие запросы передают токен в заголовке `X-CSRF-Token`.
- Сервер проверяет CSRF-токен и допустимый same-origin `Origin`.
- CSRF-защита обязательна для изменения профиля, предметов, задач, пароля и выхода.
- После нового входа создаётся новый CSRF-токен.
- CSRF-токен не попадает в журналы.
- После 5 неудачных попыток входа за 15 минут сочетание нормализованного логина и IP-адреса блокируется на 15 минут; успешный вход сбрасывает счётчик.
- Постоянная блокировка аккаунта не применяется, а сообщение не раскрывает существование логина.
- Журналы не содержат пароли, хеши паролей, session token, cookie, секреты и полные чувствительные заголовки.
- Cookie сессии передаётся только по HTTPS и недоступна JavaScript.
- Обычный выход отзывает текущую сессию; выход на всех устройствах, смена пароля и административный сброс пароля отзывают все действующие сессии.

## 14. Резервное копирование

- Ежедневная резервная копия создаётся в `23:50` по часовому поясу `Europe/Moscow`.
- Хранятся последние 30 ежедневных копий.
- Перед миграциями базы и значимыми обновлениями API создаётся отдельная ручная копия.
- Резервное копирование SQLite выполняется через SQLite backup API или эквивалентный безопасный согласованный механизм.
- Нельзя считать корректной резервной копией случайное копирование только основного файла активной базы, работающей в WAL-режиме.
- Резервные копии хранятся вне каталога статического сайта, в `/var/backups/levelup-api`.
- Доступ к резервным копиям ограничивается системными правами.
- Процедура считается готовой только после отдельной практической проверки восстановления базы после первоначальной настройки.
- Затем проверка восстановления выполняется раз в три месяца.
- Проверка восстановления должна подтверждать целостность пользователей, профилей, предметов, задач, версий, удалений и сессий в пределах принятой политики.
- Старые ежедневные копии старше 30 дней удаляются автоматически.
- Создание и удаление резервных копий журналируются без секретов.

## 15. Предполагаемые изменения интерфейса

Позднее клиентскому приложению потребуются:

- проверка сессии до показа основного интерфейса;
- форма входа и экран повторного входа без очистки незавершённого ввода;
- обязательный экран первоначальной смены временного пароля и ввода отображаемого имени;
- кнопки выхода и «Выйти на всех устройствах»;
- форма обычной смены пароля с текущим паролем, новым паролем и его повтором;
- изменение отображаемого имени в настройках;
- состояния первоначальной загрузки;
- состояние выполняющегося сохранения;
- сообщения об ошибках сервера;
- сообщение об отсутствии сети;
- постоянное уведомление об устаревших данных;
- кнопка «Обновить»;
- предупреждение о несохранённом вводе перед обновлением;
- блокировка повторных действий на время запроса;

Существующие функции задач, XP, фильтров и календаря должны сохранить согласованное поведение после замены локального источника данных серверным.

## 17. Наследование бизнес-правил MVP

- Серверная версия обязана сохранить все подтверждённые правила текущего Level Up.
- Сервер повторно проверяет все инварианты, реализованные в `script.js` и зафиксированные в `concept.md` и `tz.md`.
- Переход на серверное хранение автоматически не меняет направления задач.
- Не меняются правила обязательности предмета, базовые и дополнительные предметы.
- Не меняются сложности и награды: `easy` — 5 XP, `medium` — 20 XP, `hard` — 50 XP.
- Не меняются правила выполнения, однократного начисления XP, удаления и пересчёта XP и уровня.
- `originalDeadline` остаётся первоначальным неизменяемым дедлайном.
- `currentDeadline` остаётся актуальным изменяемым дедлайном.
- `postponementCount` изменяется только по действующему правилу переноса на более позднюю дату.
- Фильтры продолжают менять только представление и не становятся серверными изменяющими операциями.
- Календарное представление сохраняет действующее поведение и использует активные задачи.
- Новые возможности предметов или задач, отсутствующие в действующем MVP, не добавляются.
- Любое изменение существующего бизнес-правила требует отдельного решения и предварительного обновления `concept.md` и `tz.md`.

## 18. Критерии готовности

Первая версия серверной синхронизации считается готовой, если выполнены все следующие условия.

### Аккаунт и доступ

- Администратор может создать закрытый личный аккаунт интерактивной командой без передачи логина или временного пароля через аргументы командной строки.
- Нормализованный логин соответствует согласованному формату и уникален.
- Пароль соответствует согласованным правилам, проверяется на очевидно слабые значения и хранится как защищённый медленный хеш, предпочтительно Argon2id.
- Пользователь входит по логину и паролю и может выйти.
- При первом входе пользователь обязан заменить временный пароль, повторить новый пароль и ввести отображаемое имя до открытия основного интерфейса.
- Обычная смена пароля требует текущий пароль, новый пароль и его повтор.
- После смены или административного сброса пароля все сессии завершены.
- Каждая сессия действует ровно 30 дней без продления фоновой активностью и сохраняется после закрытия браузера.
- Приложение проверяет сессию до показа основного интерфейса.
- Истечение сессии блокирует изменения и открывает повторный вход без очистки незавершённого ввода.
- Обычный выход завершает текущую сессию, а «Выйти на всех устройствах» — все сессии.
- Одновременно действует не более 10 сессий; одиннадцатая завершает самую старую.
- Сессионная cookie использует `Secure`, `HttpOnly`, `SameSite=Lax`, а изменяющие запросы защищены отдельным CSRF-токеном в памяти страницы и проверкой `Origin`.
- Все запросы ограничены `userId` текущей авторизованной сессии.
- Архитектура допускает добавление других пользователей без переделки пользовательских таблиц.
- После 5 неудачных попыток за 15 минут сочетание логина и IP блокируется на 15 минут без раскрытия существования аккаунта.

### Развёртывание и безопасность

- Приложение работает через `https://levelup.aikcu.ru`, а REST API v1 доступен через `/api/v1/` того же origin.
- Uvicorn слушает только `127.0.0.1:8000`.
- Новые внешние порты не открыты.
- API, SQLite, секреты и резервные копии расположены вне `/var/www` и недоступны как статические файлы.
- Сервис работает от отдельного системного пользователя без SSH-входа и с ограниченными правами.
- В Git и журналах отсутствуют пароли, токены и секреты.
- Публичный CORS не включён, попытки входа ограничены.
- Базовые маршруты авторизации, полного состояния, проверки `syncVersion` и операций с задачами соответствуют настоящему документу.
- Ошибки API используют согласованные коды и не раскрывают пути, стек или секреты.

### Данные и бизнес-логика

- Профиль, предметы и задачи хранятся с привязкой к `userId`.
- Сервер проверяет все поля, допустимые значения и инварианты текущей модели Level Up.
- Задачи являются источником истины для `totalXp` и `level`.
- `xpReward` всегда соответствует сложности.
- Выполнение одной задачи не может начислить XP повторно.
- Удаление выполненной задачи корректно пересчитывает XP, уровень и прогресс.
- `originalDeadline` остаётся неизменным, а перенос на более позднюю дату увеличивает `postponementCount` по согласованному правилу.
- Повтор изменяющего запроса с тем же идентификатором операции не создаёт дополнительный эффект.
- Все изменяющие операции требуют случайный UUID в `Idempotency-Key`; ключ, отпечаток и результат хранятся 24 часа в одной транзакции с изменением.
- Профиль, предметы и задачи начинают с `version: 1`, возвращают `ETag` и увеличивают версию после каждого успешного изменения.
- Изменение и удаление требуют `If-Match`.
- Дедлайны рассчитываются по `Asia/Irkutsk`, а технические временные метки хранятся в UTC.
- Сервер сохраняет все действующие бизнес-правила MVP без добавления новых возможностей задач или предметов.

### Синхронизация и конфликты

- Данные сервера загружаются при запуске и по кнопке «Обновить».
- Полный снимок `GET /api/v1/state` содержит профиль, предметы, неудалённые задачи, XP, уровень, `syncVersion` и серверное время.
- Открытая страница примерно раз в 30 секунд, при возврате на вкладку и после восстановления окна проверяет `syncVersion`.
- Изменения другого устройства вызывают постоянное уведомление, но не заменяют открытые данные автоматически.
- При незавершённом вводе обновление требует подтверждения пользователя.
- Изменение одной задачи не создаёт конфликт с независимым изменением другой задачи.
- Устаревшее изменение той же записи отклоняется и не затирает актуальные данные молча.
- Отсутствующий `If-Match` возвращает `428`, устаревшая версия — `412`, удалённая запись — `410`, чужая запись — `404`.
- Удалённая задача не восстанавливается устаревшим устройством.
- Создание, редактирование, выполнение и удаление на одном устройстве становятся доступны второму после обнаружения версии и ручного обновления.

### Ошибки и отсутствие сети

- Уже загруженные данные остаются доступными для просмотра без интернета.
- `localStorage` содержит только последний подтверждённый сервером снимок и не содержит паролей, cookie, session token или CSRF token.
- При доступном кэше показывается сообщение «Нет соединения. Показаны данные, загруженные ранее»; без кэша показывается ошибка подключения.
- Изменяющие действия без связи не объявляются сохранёнными.
- Офлайн-очередь отсутствует, и интерфейс прямо сообщает об этом поведении.
- Во время запроса повторные действия блокируются.
- Ошибка или повтор запроса не создают дубликаты и не повторяют бизнес-эффект.
- Повреждённый локальный кэш или некорректный ответ не удаляют серверные данные.
- После восстановления связи серверное состояние заменяет локальный кэш.

### Удаление и резервное копирование

- Удаление является мягким, записывает `deletedAt` и сразу скрывает запись после подтверждения сервера.
- Мягко удалённые задачи хранятся 30 дней и недоступны для пользовательского восстановления.
- Окончательная очистка выполняется отдельным обслуживанием.
- Резервная копия создаётся согласованным способом для SQLite и хранится вне сайта.
- Ежедневная копия создаётся в `23:50` по `Europe/Moscow`, хранятся последние 30 ежедневных копий, а старые удаляются автоматически.
- Перед миграциями базы и значимыми обновлениями API создаётся отдельная ручная копия.
- Выполнена успешная первоначальная проверка восстановления, последующие проверки запланированы раз в три месяца.
- Создание и удаление копий журналируется без секретов.

### Переход и приёмка

- Серверный аккаунт начинает с пустого состояния; тестовый `levelUpState` не импортируется.
- Старый `localStorage` не удаляется автоматически до окончания проверки.
- Все текущие сценарии задач, предметов, XP, фильтров и календаря работают с серверными данными.
- Проверены одновременная работа компьютера и телефона, конфликт одной записи, независимые изменения разных задач, удаление, повтор запроса, потеря и восстановление сети.
- После перезагрузки страницы серверные данные восстанавливаются корректно.
- В браузере отсутствуют необработанные ошибки приложения, а интерфейс сообщает о загрузке, сохранении, ошибках и устаревших данных понятным текстом.
